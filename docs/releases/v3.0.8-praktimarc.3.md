# v3.0.8-praktimarc.3

Release date: 2026-10-01

`3.0.8-praktimarc.3` is the first published Praktimarc release after `3.0.8-praktimarc.1`.

## Release lineage

`3.0.8-praktimarc.2` existed in the repository as an intermediate source version after the binary-file-download work, but it was never tagged and no GitHub Release was published for it. The exact `.2` source baseline is commit `d61d6157daa0164d7527f77ae321ce538aa67f1e`.

Therefore `.3` contains two groups of changes:

1. the binary-safe file-download functionality that had already been present in the unpublished `.2` source line; and
2. the transport, lifecycle, protocol, concurrency, and public-exception hardening added after that `.2` source baseline.

This avoids publishing an artificial `.2` retroactively after the source tree has already advanced to the hardened API contract.

## Changes since the unpublished `.2` source baseline

### Concurrent use of one `ApiConnection`

- Multiple synchronous, asynchronous, and binary-read operations may be active on one connection at the same time.
- Complete RouterOS command sentences are serialized internally on the shared output stream so command words cannot interleave.
- The write lock covers only the command write and fatal send transition; it is not held while waiting for RouterOS replies.
- A send-side `IOException` changes the connection to the fatal failed state before the write lock is released, preventing a waiting writer from sending on a broken session.

### Leak-free command lifecycle

- `!done` removes the listener registration before `completed()` is invoked.
- `!trap` and the retained legacy `!halt` path remove the listener registration before `error(...)` is invoked.
- A later `!done` after a command error is ignored for the already-terminal registration.
- Synchronous timeout removes the local registration instead of leaving a listener behind.
- A local timeout deliberately does not send RouterOS `/cancel`; cancellation remains an explicit caller action.
- Listener registration is rolled back when the command write fails.

### Fatal connection-loss propagation

- EOF, socket loss, unrecoverable framing/protocol errors, RouterOS `!fatal`, and fatal send failures terminate the complete API session.
- All still-active text and binary operations receive a terminal `ApiConnectionException` rather than waiting until timeout.
- New commands fail promptly after a fatal session transition and are not written to the old stream.
- `ConnectionListener` provides an additive public lifecycle notification for unexpected connection loss even when no command is active.
- A listener registered after an already-recorded fatal loss is notified immediately with the retained failure.
- Intentional `close()` does not emit `ConnectionListener.connectionLost(...)`.
- `close()` is idempotent.
- There is no automatic reconnect, command replay, or transparent session replacement.

### Stable public low-level exception API

New consumers no longer need to compile against `me.legrange.mikrotik.impl.*` in order to classify failures.

The public hierarchy is:

- `ApiConnectionException` — transport, connection, and session-fatal failure;
- `ApiCommandException` — RouterOS command-level failure, including command tag and category metadata;
- `ApiDataException` — malformed or inconsistent API data when the failure can safely be scoped without losing session routing.

`ApiCommandException.hasCategory()` distinguishes a real RouterOS category `0` from an omitted category. `getCategory()` remains integer-compatible and returns `0` when the category was absent.

The previous impl-package exception classes remain as compatibility subclasses of the new public types.

Synchronous command failures now preserve and throw the concrete API exception directly instead of wrapping it in a new generic `MikrotikApiException`. Existing code that catches the common base type continues to work, while consumers can now catch the stable specialized public types directly.

### RouterOS protocol vocabulary and failure scope

The dispatcher explicitly supports:

- `!re` — command data;
- `!empty` — valid no-data reply introduced by RouterOS 7.18; non-terminal until `!done`;
- `!done` — normal command completion;
- `!trap` — RouterOS command error;
- `!halt` — retained legacy compatibility, treated like a command error;
- `!fatal` — whole-session fatal error, including best-effort extraction of free-word diagnostics.

Unknown reply words, duplicate or untrustworthy tag routing, reserved/unsupported control bytes, truncated framing, and other unrecoverable protocol states now fail the session instead of being silently ignored. A malformed but uniquely tagged command reply can still be failed locally with `ApiDataException` when routing remains trustworthy.

## Changes included from the unpublished `.2` source line

Compared with the last published release, `3.0.8-praktimarc.1`, `.3` also includes the binary-file-download work that had been staged as `.2` source code:

- `ApiConnection.downloadFile(...)` for binary-safe RouterOS file downloads;
- RouterOS `/file/read` support for RouterOS 7.13 or newer;
- binary payload handling that does not pass arbitrary bytes through the text-oriented `String` response path;
- chunked file reads with validation of the expected final byte count;
- `.part` staging with best-effort cleanup on failure so incomplete data is not published as the final target;
- regression coverage for zero-byte, malformed, duplicate, interleaved text/binary, and RouterOS error cases;
- raw-sentence parsing improvements required for binary-safe transport.

Binary upload and a RouterOS pre-7.13 small-file fallback remain out of scope.

## Compatibility notes

The established public signatures `String execute(String, ResultListener)` and `void cancel(String)` remain unchanged. No public command-handle abstraction was introduced.

Notable intentional behavioral changes are:

- repeated `close()` is now a no-op instead of failing because the connection is already closed;
- synchronous RouterOS command errors are surfaced as their concrete public exception type rather than a generic wrapper;
- unknown or irrecoverably malformed protocol replies can fail the complete connection instead of being silently discarded;
- `!trap`/`!halt` are terminal at the Java listener API level, so callers receive `error(...)` but not a later `completed()` for the same registration;
- synchronous timeout removes the local listener registration but does not implicitly cancel the RouterOS command.

Existing consumers that catch `MikrotikApiException` remain source-compatible. New code should prefer the public specialized exceptions and should not depend on `me.legrange.mikrotik.impl.*`.

## Downstream facade boundary

This release provides the low-level guarantees required by the separate `praktimarc/mikrotik-facade` project. The facade should not need its own connection-wide send lock, duplicate RouterOS response dispatcher, or dependency on impl-package exception classes.

The following remain intentionally outside this library:

- `CompletableFuture` command APIs;
- `Flow.Publisher` streaming APIs;
- capability detection;
- RouterOS 6/7 facade adapters;
- facade-specific exception mapping;
- automatic reconnect/replay;
- a public `CommandHandle`.

## Verification and release artifacts

The release workflow runs on JDK 11 and executes:

```text
mvn -B clean verify --file pom.xml
```

The GitHub Release is published only after that verification succeeds and the expected artifacts exist. It contains:

- `mikrotik-3.0.8-praktimarc.3.jar`
- `mikrotik-3.0.8-praktimarc.3-sources.jar`
- `mikrotik-3.0.8-praktimarc.3-javadoc.jar`

An exact `release: v<project.version>` commit on `master` is treated as an explicit release request. After successful verification, the workflow creates the corresponding annotated Git tag and publishes the GitHub Release. Manually pushed matching release tags remain supported as well.
